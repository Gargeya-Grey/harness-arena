# AGENTS.md

Orientation for anyone - human or agent - working in this repository.

The repo runs the same test cases through different CLI harnesses and models, using the owner's own sign-ins (no paid API calls), then compares them side by side. Inputs (cases, prompts, model configs, experiments) are versioned; runs are immutable evidence; scores and reports are derived from runs. The CLI is `node lab`; it has no dependencies.

## Vocabulary

- **Suite** - a versioned set of test cases.
- **Prompt version** - a frozen template that runs reference by id and version.
- **Harness** - the CLI that makes the call: built in (`claude-code`, `codex`, `command-code`, `gemini-cli`, `opencode`) or declared in `configs/harnesses.yaml`.
- **User setup** - the owner's own harness configuration (global instructions, skills, MCP servers). An experiment sets `user_config: loaded` (default) or `isolated`; the run records the flags that kept it out.
- **Target** - one model key through one harness, declared in an experiment.
- **Configuration** - model + harness + harness version + effort + user setup; the unit the dashboard compares.
- **Experiment** - a declared comparison: suite, prompt, targets, repeats, evaluators.
- **Run** - one execution of an experiment through one harness, stored under `results/<run_id>/`.
- **Raw result** - one model response with latency, tokens, cost, and error.
- **Score** - one evaluator verdict on one raw result.

## Layout

```
lab/cli.mjs               Entry point: node lab <command>
lab/adapters/             cli.mjs is the one harness seam; one file per built-in harness; declared.mjs; index.mjs registers them
lab/evaluators/index.mjs  Versioned evaluators
lab/commands/             run, score, validate, doctor/runs/report
lab/lib/                  yaml.mjs, schema.mjs (subsets), metrics.mjs, state.mjs (derived view)
dashboard/server.mjs      Local server: /api/state, /api/artifact, annotations, boards, /api/catalog, /api/jobs
dashboard/jobs.mjs        Starts allowlisted `node lab` commands for the control page (no shell)
dashboard/public/         Static UI, no build step: index.html control page, compare.html comparison
configs/models.yaml       Model registry: exact id, params, optional pricing, harness_models
configs/harnesses.yaml    CLI harnesses declared with no code
datasets/<suite>/         suite.yaml + cases.jsonl (one case per line); agent suites add workspaces/ and checks/
prompts/<prompt>/         prompt.yaml + frozen vN.yaml templates
experiments/*.yaml        targets x suite x prompt x repeats x evaluators
results/<run_id>/         Immutable run: run.json, raw.jsonl, scores/ (+ harness-events.ndjson, local only)
reports/                  Derived aggregates: regenerate rather than edit

tests/                    node:test files; fixtures/repo is generated by fixtures/make-fixtures.mjs
docs/strategy.md          Authoritative principles, IDs, lifecycle, dimensions
docs/dashboard-spec.md    Dashboard design: UI, data contract, visual system
.agents/skills/verify-model-lab/   How to launch, drive and prove the CLI and dashboard
```

## Sources of truth

- **Structural changes** (datasets, prompts, schemas, experiments, result format): read `docs/strategy.md` first.
- **Dashboard changes**: read `docs/dashboard-spec.md` first.
- **Writing or changing a record**: read the matching `schemas/*.schema.json` first.
- **Proving a change**: follow `.agents/skills/verify-model-lab/SKILL.md`.
- **Human overview**: `README.md`.

## Invariants

1. Treat `results/` as append-only evidence. A correction is a new run with a new `run_id`. New runs and annotations go to the data folder (`data_dir` in `lab.local.yaml`, or `LAB_DATA`), outside git; runs committed in `results/` are still read. Never delete a run folder in either place. One `run`, `--resume` or `score` at a time holds the run store lock (`.lab-run.lock` in the data folder, in `results/` and beside the evidence ledger); a second one is refused. The evidence ledger `lab.ledger.jsonl` (main checkout, not committed) records what each run wrote; only the runner, `score` and `adopt` append to it, and a run that does not match it is never scored or counted. Never edit it by hand; `node lab adopt <run-id>` is how the owner vouches for a run.
2. Keep raw and derived separate: `raw.jsonl` holds model responses; scores and `reports/` are recomputed from it without new model calls.
3. Pin exact provider snapshots in `configs/models.yaml`. Give every params variant its own `model_key`. Effort is set per target in the experiment (`effort: high` or `efforts: [low, high]`); the registry's `reasoning_effort` is only the default when a target sets none. Each effort runs as its own run and shows as its own configuration.
4. Hold suite version, prompt version, evaluator versions, and decoding params constant within a comparison. Changing one means a new experiment and a new run.
5. Reuse IDs exactly. `case_id` is `<suite>-<slug>`, `model_key` is a registry key, prompt versions are quoted strings (`"1"`). Never renumber or repurpose an ID.
6. Write every record to the schema in `schemas/`.
7. Keep files Windows-safe and diff-friendly: UTF-8, LF, compact JSONL (one object per line), ISO 8601 UTC timestamps ending in `Z`, and no `: ? * " < > |` in filenames.
8. Never spawn a harness through a shell. Pass the prompt on stdin or as one argument (`lab/adapters/process.mjs`).
9. Live model calls cost money or subscription quota. Use `--dry-run`, the fixtures, or a one-case run (`--repeats 1 --cases <id>`) unless the owner asked for a full run.

## Tasks

### Add or change test cases

1. Start with `node lab new-case <suite> <slug>` (`--agent` for an agent task), or edit `datasets/<suite>/cases.jsonl` by hand; keep `case_id` stable and unique. `validate` fails while a `<<FILL IN>>` marker is left.
2. Bump `version` in `suite.yaml`.
3. Give every case an `input` object matching the prompt's `variables`.
4. For an agent task, set `input.workspace` to a folder in `datasets/<suite>/workspaces/` (the starter project) and `expected.check` to a folder in `datasets/<suite>/checks/` with `probe.mjs` (exports `probes: [{ name, run({ load }) }]`; each returns a value) and `expected.json` (`{ probes: { <name>: <value> }, files: { <path>: { exists, includes, same_as_starter } } }`). The agent never sees the check, and the sandbox never sees `expected.json`. Its experiment needs `access: edit` and `workdir: isolated`.

Done when `node lab validate` passes.

### Add a model

1. Add an entry to `configs/models.yaml`: provider, exact id, params, pricing (with where and when the price was read).
2. If a harness needs a different id, add it under `harness_models: { <harness>: <id> }`.
3. Reference the key in an experiment target.

Done when `node lab validate` passes and `node lab run <experiment> --dry-run` shows the expected model id per harness.

### Add a harness

First choice, no code: add an entry to `configs/harnesses.yaml` (the file documents every field). It covers a CLI that prints its answer as text, one JSON object, or JSON lines.

A CLI that needs real parsing (answer spread over events, tool counts, usage summed over turns) gets a built-in adapter:

1. Copy the closest file in `lab/adapters/` (`opencode.mjs` for JSON events). Give `defineCli` (`lab/adapters/cli.mjs`) a `bin`, `args`, `parse`, and, when the CLI has flags that skip the user setup, `isolation`.
2. Register it in `lab/adapters/index.mjs`.
3. Save one real output under `tests/fixtures/harness/` (remove local paths and private context) and add a parse test in `tests/adapters.test.mjs`.

Done when `npm test` and `node lab validate` pass, `node lab doctor` lists it as ready, and one live one-case run completes.

### Change a prompt

1. Add `prompts/<prompt>/v<N+1>.yaml`.
2. Point `current` in `prompt.yaml` at the new version.
3. Reference the new version in a new experiment.

Done when existing runs still point at the version they recorded and no frozen template changed.

### Declare a comparison

1. Copy an experiment file. Set `suite`, `prompt`, `targets` (`- model: <key>` / `harness: <name>`, optional `effort: <level>` or `efforts: [<level>, ...]`, `default` for the harness default), `repeats`, and `evaluators`. Add a `cases` list to run a subset.
2. For a controlled comparison, change one axis only: same model through two harnesses, two models through one harness, or one model at several efforts (`efforts: [low, medium, high]`).
3. Use 3 or more cases, and 3 or more repeats when reliability matters. The dashboard shows confidence intervals only from 3 cases; repeats of one case are not more cases.

Done when `node lab validate` passes and `--dry-run` lists every target.

### Execute a run

`node lab run experiments/<name>.yaml`. The runner writes only under `results/<run_id>/`: `run.json` with `status: running` and input hashes, one raw row per model x case x repeat (failures included with `error` set), the harness event stream, then `completed` or `failed`, then scores.

A run that stopped before its last row (crashed: `stale` in `node lab runs`; or stopped by the user) continues with `node lab run --resume <run_id>`: it appends only the missing rows, and refuses when an input changed.

Done when `node lab validate` passes and `node lab runs` shows the run with every expected row.

### Run the dashboard

```bash
node lab dashboard
```

Open `http://127.0.0.1:4317`: the control page (run, score, validate, doctor) with the comparison under Compare (`/compare.html`). The server binds to localhost only, refuses other Host headers and cross-site writes, and indexes `results/` on every `/api/state` request. A new job command goes in the allowlist in `dashboard/jobs.mjs` with argument checks and a test in `tests/jobs.test.mjs`.

Done when `/api/state` lists the expected contexts and configurations and the browser renders them. To work on the UI without live data: `LAB_ROOT=tests/fixtures/repo node lab dashboard --port 4318`.

### Check everything

```bash
npm test
node lab validate
LAB_ROOT=tests/fixtures/repo node lab validate
```

After changing `tests/fixtures/make-fixtures.mjs`, run `npm run fixtures` to regenerate `tests/fixtures/repo`.

## Non-goals (for now)

Local models, LLM-as-judge, retries and caching, parallel execution, multi-turn conversations, and database storage. JSONL plus git is the intended store until volume forces a change.
