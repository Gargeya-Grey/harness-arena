# AGENTS.md

Orientation for anyone - human or agent - working in this repository.

The repo runs the same test cases through different CLI harnesses and models, using the owner's own sign-ins (no paid API calls), then compares them side by side. Inputs (cases, prompts, model configs, experiments) are versioned; runs are immutable evidence; scores and reports are derived from runs. The CLI is `node lab`; it has no dependencies. The comparison suites form the difficulty ladder: 80 tasks in five tiers (`docs/difficulty.md`).

## Vocabulary

- **Suite** - a versioned set of test cases. An active suite lives in `datasets/<id>/`. A retired suite lives in `datasets/archive/<id>/`: old runs still name it, so it still loads, validates and scores.
- **Ladder** - the 80 tasks in five tiers (easy, medium, hard, extra-hard, supreme) over the suites `ladder-answer`, `ladder-code` and `ladder-agent`. `configs/ladder.yaml` holds the tier table. Every ladder case records its tier and its expert time in `metadata.tier`.
- **Pilot** - a ladder run with `--repeats 1`. `node lab ladder --calibrate` reads it and says what each task can tell about the configurations that ran it.
- **Prompt version** - a frozen template that runs reference by id and version.
- **Harness** - the CLI that makes the call: built in (`claude-code`, `codex`, `command-code`, `gemini-cli`, `opencode`) or declared in `configs/harnesses.yaml`.
- **User setup** - the owner's own harness configuration (global instructions, skills, MCP servers). An experiment sets `user_config: loaded` (default) or `isolated`; the run records the flags that kept it out.
- **Target** - one model key through one harness, declared in an experiment.
- **Configuration** - model + harness + harness version + effort + user setup; the unit the dashboard compares.
- **Experiment** - a declared comparison: suite, prompt, targets, repeats, evaluators.
- **Run** - one execution of an experiment through one harness, stored under `results/<run_id>/`.
- **Raw result** - one model response with latency, tokens, cost, and error.
- **Score** - one evaluator verdict on one raw result.

## Invariants

1. Treat `results/` as append-only evidence. A correction is a new run with a new `run_id`. New runs and annotations go to the data folder (`data_dir` in `lab.local.yaml`, or `LAB_DATA`), outside git; runs committed in `results/` are still read. Never delete a run folder in either place. Retire a suite by moving it to `datasets/archive/<id>/` with every byte unchanged (the suite hash in old runs covers `suite.yaml`, `cases.jsonl`, `workspaces/` and `checks/`). A new suite version first freezes the old one (`node lab freeze <suite>`, to `datasets/<suite>/versions/<version>/`); `score` judges a run only by the exact suite it recorded. A suite id never exists in both places; `validate` refuses it. One `run`, `--resume` or `score` at a time holds the run store lock (`.lab-run.lock` in the data folder, in `results/` and beside the evidence ledger); a second one is refused. The evidence ledger `lab.ledger.jsonl` (main checkout, not committed) records what each run wrote; only the runner, `score` and `adopt` append to it, and a run that does not match it is never scored or counted. Never edit it by hand; `node lab adopt <run-id>` is how the owner vouches for a run.
2. Keep raw and derived separate: `raw.jsonl` holds model responses; scores and `reports/` are recomputed from it without new model calls.
3. Pin exact provider snapshots in `configs/models.yaml`. Give every params variant its own `model_key`. Effort is set per target in the experiment (`effort: high` or `efforts: [low, high]`); the registry's `reasoning_effort` is only the default when a target sets none. Each effort runs as its own run and shows as its own configuration.
4. Hold suite version, prompt version, evaluator versions, and decoding params constant within a comparison. Changing one means a new experiment and a new run.
5. Reuse IDs exactly. `case_id` is `<suite>-<slug>`, `model_key` is a registry key, prompt versions are quoted strings (`"1"`). Never renumber or repurpose an ID.
6. Write every record to the schema in `schemas/`.
7. Keep files Windows-safe and diff-friendly: UTF-8, LF, compact JSONL (one object per line), ISO 8601 UTC timestamps ending in `Z`, and no `: ? * " < > |` in filenames.
8. Never spawn a harness through a shell. Pass the prompt on stdin or as one argument (`lab/adapters/process.mjs`).
9. Live model calls cost money or subscription quota. Use `--dry-run`, the fixtures, or a one-case run (`--repeats 1 --cases <id>`) unless the owner asked for a full run.

## Tasks

### Add or change test cases

This section is for the smoke suite and for any new suite. The ladder suites are generated: see "Add or change a ladder task". An archived suite takes no new case (`new-case` refuses it).

1. Start with `node lab new-case <suite> <slug>` (`--agent` for an agent task), or edit `datasets/<suite>/cases.jsonl` by hand; keep `case_id` stable and unique. `validate` fails while a `<<FILL IN>>` marker is left.
2. Bump `version` in `suite.yaml`; `new-case` does it for you. Before a change by hand, run `node lab freeze <suite>`: it copies the version to `datasets/<suite>/versions/<version>/`, so its runs still score and show (`docs/strategy.md`, Frozen suite versions). `new-case` freezes first too.
3. Give every case an `input` object matching the prompt's `variables`.
4. For an agent task, set `input.workspace` to a folder in `datasets/<suite>/workspaces/` (the starter project) and `expected.check` to a folder in `datasets/<suite>/checks/` with `probe.mjs` (exports `probes: [{ name, run({ load }) }]`; each returns a value) and `expected.json` (`{ probes: { <name>: <value> }, files: { <path>: { exists, includes, same_as_starter } } }`). The agent never sees the check, and the sandbox never sees `expected.json`. Its experiment needs `access: edit` and `workdir: isolated`.

Done when `node lab validate` passes.

### Add or change a ladder task

The ladder suites (`ladder-answer`, `ladder-code`, `ladder-agent`) are built from definitions. `cases.jsonl` is output: never edit it by hand. Read `docs/difficulty.md` first (the scale and the rules for a task).

1. Write or edit one definition under `datasets/<suite>/defs/` (any depth; a file name that starts with `_` is a helper). It sets `slug`, `tier` (`level`, `human_minutes` inside the tier's range in `configs/ladder.yaml`, and a `basis` that says how the time was estimated), and the fields of its suite: `question` and `answer` for `ladder-answer`; name, signature, task and tests for `ladder-code`; `task` for `ladder-agent`.
2. Make the reference. `ladder-answer`: the answer comes from code in the definition. `ladder-code`: a reference solution in `tests/fixtures/ladder-code-solutions/<defs subfolder>/<case_id>.mjs`; a test without `returns` takes its value from it. `ladder-agent`: a starter project in `datasets/ladder-agent/workspaces/<slug>/`, a hidden check in `checks/<slug>/` (`probe.mjs` and `expected.json`), and a reference solution in `tests/fixtures/ladder-agent-solutions/<defs subfolder>/<slug>/`.
3. Run `node lab freeze <suite>` first, unless the current version was never run. Run `node datasets/<suite>/generate.mjs --write`, then bump `version` in `suite.yaml`. `--check` exits 1 when `cases.jsonl` is not what the definitions give.
4. Add or update the test in `tests/ladder-<kind>-*.test.mjs`: the reference passes, and a plausible wrong answer does not.

Moving a task keeps its `case_id`; only its tier changes, in a new suite version, and the definition records `tier.moved: { from, evidence }`. Retiring a task is one line in `datasets/<suite>/defs/_retired.mjs` (slug and reason); its definition and proofs stay, so the `case_id` stays taken. A tier must keep the task counts of `configs/ladder.yaml`.

Done when `node lab validate` and `npm test` pass, and `node lab ladder` prints no ladder problem (it lists them first).

### Run the ladder and read it

```bash
node lab run experiments/ladder-answer.yaml --dry-run   # also ladder-code, ladder-agent
node lab run experiments/ladder-code.yaml --repeats 1   # the pilot: one repeat per task
node lab ladder                                         # configurations as rows, tiers as columns
node lab ladder --calibrate                             # per task: information class; per pair: shared tasks
```

`node lab ladder` reads only the rows that count (closed, ledger-matched, scored runs), as the dashboard counts them. Unlike the dashboard, it pools the runs of one suite version across experiments: per suite, the newest version that has counted runs, or the one `--suite-version <suite>@<version>` names (repeat or comma-separate it). It prints which version of each suite it used and how many counted runs of other versions it left out. A suite version whose counted runs mix prompt versions is refused: pick runs with `--runs`. A cell is `solved/counted`, then the mean score. A task counts as solved when its mean score over the configuration's counted repeats is 1. A `*` marks a configuration that has results for fewer tasks than the tier holds. `--suite <ladder suite>` and `--runs <id,...>` filter; `--json` prints the same data.

`--calibrate` prints what the runs can tell, as `docs/difficulty.md` defines it. Each task gets one information class: `no-data`, `one-config`, `all-solved`, `all-unsolved` or `disagree`. Each pair of configurations gets the tasks both ran, the tasks only one of them solved, and an exact two-sided sign test on those two counts. A tier is an estimate label: the lab gives no target score and no verdict on a task. It flags a task when, of two configurations that both ran it, the one with the higher mean on the other tasks both ran scores under 0.5 on every repeat while the other scores 1 on every repeat: check that task for a defect before anything else. A task changes tier only when the expert-time estimate was wrong, and only in a new suite version.

Done when `node lab ladder` shows the runs you expect and `node lab validate` passes.

### Add a model

1. Add an entry to `configs/models.yaml`: provider, exact id, params, pricing (with where and when the price was read).
2. If a harness needs a different id, add it under `harness_models: { <harness>: <id> }`.
3. Reference the key in an experiment target.

Done when `node lab validate` passes and `node lab run <experiment> --dry-run` shows the expected model id per harness.

### Add a harness

First choice, no code: add an entry to `configs/harnesses.yaml` (the file documents every field). It covers a CLI that prints its answer as text, one JSON object, or JSON lines.

A CLI that needs real parsing (answer spread over events, tool counts, usage summed over turns) gets a built-in adapter:

1. Copy the closest file in `lab/adapters/` (`opencode.mjs` for JSON events). Give `defineCli` (`lab/adapters/cli.mjs`) a `bin`, `args`, `parse`, and, when the CLI has flags that skip the user setup, `isolation`.
2. Register it in `lab/adapters/index.mjs`.
3. Save one real output under `tests/fixtures/harness/` (remove local paths and private context) and add a parse test in `tests/adapters.test.mjs`.

Done when `npm test` and `node lab validate` pass, `node lab doctor` lists it as ready, and one live one-case run completes.

### Change a prompt

1. Add `prompts/<prompt>/v<N+1>.yaml`.
2. Point `current` in `prompt.yaml` at the new version.
3. Reference the new version in a new experiment.

Done when existing runs still point at the version they recorded and no frozen template changed.

### Declare a comparison

1. Copy an experiment file. Set `suite`, `prompt`, `targets` (`- model: <key>` / `harness: <name>`, optional `effort: <level>` or `efforts: [<level>, ...]`, `default` for the harness default), `repeats`, and `evaluators`. Add a `cases` list to run a subset.
2. For a controlled comparison, change one axis only: same model through two harnesses, two models through one harness, or one model at several efforts (`efforts: [low, medium, high]`).
3. Use 3 or more cases, and 3 or more repeats when reliability matters. The dashboard shows confidence intervals only from 3 cases; repeats of one case are not more cases.

Done when `node lab validate` passes and `--dry-run` lists every target.

### Execute a run

`node lab run experiments/<name>.yaml`. The runner writes only under `results/<run_id>/`: `run.json` with `status: running` and input hashes, one raw row per model x case x repeat (failures included with `error` set), the harness event stream, then `completed` or `failed`, then scores.

A run that stopped before its last row (crashed: `stale` in `node lab runs`; or stopped by the user) continues with `node lab run --resume <run_id>`: it appends only the missing rows, and refuses when an input changed.

Done when `node lab validate` passes and `node lab runs` shows the run with every expected row.

### Run the dashboard

```bash
node lab dashboard
```

Open `http://127.0.0.1:4317`: Home, Run and Lab on the control page, and Results (`/results.html`) for one test at a time. Old `/compare.html` links forward to Results. The server binds to localhost only, refuses other Host headers and cross-site writes, and indexes `results/` on every `/api/state` request. The Run page and the job list offer the experiments at the top of `experiments/`; a retired one in `experiments/archive/` runs from the terminal by path. A new job command goes in the allowlist in `dashboard/jobs.mjs` with argument checks and a test in `tests/jobs.test.mjs`.

Done when `/api/state` lists the expected contexts and configurations and the browser renders them. To work on the UI without live data: `LAB_ROOT=tests/fixtures/repo node lab dashboard --port 4318`.

### Check everything

```bash
npm test
node lab validate
LAB_ROOT=tests/fixtures/repo node lab validate
```

After changing `tests/fixtures/make-fixtures.mjs`, run `npm run fixtures` to regenerate `tests/fixtures/repo`.

## Non-goals (for now)

Local models, LLM-as-judge, retries and caching, parallel execution, multi-turn conversations, and database storage. JSONL plus git is the intended store until volume forces a change.
